# How I used AI to build this

Tools: Claude Code in VS Code. The model the app itself calls is described in the README.

`CLAUDE.md` is my own working agreement. I wrote the final draft, refined with Claude, from a preflight conversation held before any code. It fixes the scope, the six-step pipeline and its rules (code computes, the model explains, the UI shows receipts), and the way of working: one small piece at a time, a plain explanation after each, a mode where I write and the assistant reviews, and I make the git commits. I added one rule later: Python at a beginner to intermediate level.

## What I wrote myself

- **CLAUDE.md.** The scope, the architecture and its rules, and the way of working. I wrote the final draft, refined with Claude from a preflight conversation, before any code.
- **First drafts** of `main.py` (the `GET /summary` route) and of an `execute.py` skeleton. Both were reviewed and then built out in small steps.
- **The design decisions** in `docs/DECISIONS.md`: no rate table, per-currency limits, one retry for a rejected plan, a stricter verifier, the hybrid answer, our own `.env` reader, 36 tests with 8 headline tests, and the eval set as the one extra.
- **Review and testing:** questions on the verifier's limits, browser testing of the screens, and the commits and pushes.
- **Small edits:** `.gitignore`.

The rest was written by the assistant and explained one piece at a time: the remaining backend, the tests, the prompts, the frontend and the README text. I reviewed each piece, asked questions, and changed or rejected what did not fit.

## What I verified

Tests run, hand calculations compared with the app, and checks on the data.

- M0: counted rows, blanks, negatives, currencies and statuses with a short stdlib script. No tests existed yet.
- M1: `build_summary` compared with an independent exact-decimal calculation on the real CSV (all 3 currency totals and 9 currency-and-status rows matched). 3 tests passed (a hand-calculated frame, missing PO and approver, `/summary` on the real data).
- M2: plan checks tried on 9 hand-made plans (5 rejected, 4 accepted, as expected). All 10 prompt examples parse as valid plans. 7 real questions run against `qwen2.5:7b-instruct` for each prompt version (v1 to v3). The three error paths (Ollama unreachable, timeout, unknown model) each produce a readable error. All of this was run by hand. Plan accuracy is not measured: 7 questions, tuned on.
- M3: 12 tests pass (policy text is verbatim, the prompt menu matches the policy ids, validation reports a bad column, value, operator and section together, the currency repair, five execution cases against hand-calculated frames). On real data: filter counts match the M0 profile, sums match `/summary`, a count by approver adds up to 140 including the missing group, and rows convert to JSON.
- M4: 33 tests pass (verifier checks, the fallback passes its own verification on a real top-5 result, rendered rows, six pipeline cases with a fake model, the `/ask` contract, out-of-scope decline, 422 and 503, the `.env` reader). Live, with `qwen2.5:7b-instruct`: 9 questions read against the data (one wrong top-5 answer found and fixed by the hybrid), then the real pipeline on 3 questions, then a real `uvicorn` server with curl on `/summary`, `/ask` and an empty question.
- M5: 36 tests pass. A mutation check broke the code 12 ways on a copy, and every break was caught by at least one test (the first run said 11 of 12 because of a script error, found and fixed). Not tested: untrusted text in the question or in data fields (the protection is structural, and one real-model attempt was planned as out of scope). The real-model trials are one-off scripts, not saved tests.
- M6: `npm run build` passes. `api.js` was checked with a pretend `fetch` on nine paths (200, 503 with and without a detail, 422, 500, 502 and 504, not JSON, network failure, cancel, timeout). The evidence component was rendered to HTML on the server with hostile sample data (an HTML tag in a vendor name stayed as text, missing values, 60 rows capped at 50, no evidence). The real model was asked three questions through the Vite proxy. I tested the screens in a browser: loading, the disabled button, the declined style, error with Retry, and the final table layout. There are no saved frontend tests, the layout was not tested at phone width, and nothing was tested in more than one browser.
- M7: the backend install and the 36 tests, and the frontend `npm ci` and `npm run build`, were run from a fresh clone of the committed repository.

Not done anywhere: an eval set, so answer quality is not measured as a number.
